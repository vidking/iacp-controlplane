Revisión comercial candidata; creación todavía bloqueada. Los catálogos de lectura se pueden consultar en esta candidata. La creación por plan_id exige primero entrega segura de la contraseña fuera de PostgreSQL y del state, capacidad autorizada y consumidores migrados. Los ejemplos siguientes no deben enviarse al runtime histórico. Authorize conserva el Bearer opaco del tenant; HTTP Basic solo permite leer esta documentación.

Consulta GET /v1/plans, GET /v1/images y GET /v1/profiles. Un producto definido no reserva capacidad: comprueba availability.available, capacity_verified y reasons. No se aumentaron cuotas de MNG.

Usa una Idempotency-Key por intención; conserva clave, cuerpo, tenant y revisión ante timeout. HTTP 202 solo confirma admisión. Ante 409 consulta el conflicto; ante 429 espera; ante 503 o timeout verifica primero si hubo admisión. No generes una nueva intención para sustituir una operación incierta.

La migración incompatible de POST no está activada; no se ofrece el cuerpo G en el Try it out histórico. Volver a referencia API.

Introducción: qué hace IACP

IACP Orchestrator es la API privada que recibe intenciones del CRM, valida el tenant, los perfiles y las políticas, registra la operación en PostgreSQL y entrega el trabajo a sus workers. El CRM decide qué necesita su cliente; IACP ejecuta y observa la infraestructura KVM autorizada en el clúster MNG.

El MVP certificado cubre catálogo de perfiles, creación asíncrona, consulta, descubrimiento de red, verificación de acceso, start, shutdown, reboot y eliminación autorizada de recursos descartables. No equivale a alta disponibilidad: la resiliencia física integral de workers, la consolidación de credenciales, OCI, LXD, IaCoC, Garbage Collector de Wasabi y extensiones comerciales siguen fuera del MVP.

No confundas los planos. El CRM usa esta API para solicitar y observar una KVM; el despliegue o rollback del propio IACP Control Plane (VM 104) es una operación de Infraestructura separada. Ningún botón de este manual modifica Compose, Terraform, credenciales, state ni las VMs protegidas.

Cuatro estados que no deben confundirse. 202 significa que la intención fue admitida. completed confirma el resultado de la operación, no que SSH o la aplicación estén disponibles. Una VM creada puede seguir apagada; una VM arrancada puede aún esperar DHCP, Cloud-Init, Guest Agent o verificación de acceso. El CRM debe consultar las observaciones antes de presentarla como lista.

Autenticación desde Swagger

  1. Entra a https://iac.cyberfuel.com/docs por HTTPS/TLS.
  2. HTTP Basic protege la lectura de esta documentación; no autoriza llamadas de negocio.
  3. Pulsa Authorize, pega solamente el Bearer del tenant autorizado y confirma. No escribas el prefijo Bearer si Swagger lo añade.
  4. Una identidad de lectura puede consultar perfiles, políticas visibles, instancias propias y operaciones propias. Una identidad de escritura adicional es necesaria para crear, Lifecycle, red, acceso y DELETE. La autorización administrativa no se concede por documentarse.
  5. Prueba una consulta segura como GET /v1/profiles. Para cerrar el acceso, vuelve a Authorize y pulsa Logout; Swagger no persiste la autorización al recargar.

No publiques tokens, contraseñas, VMID, nodos, state ni claves privadas en ejemplos, capturas o tickets.

Idempotency-Key: una intención, una clave

La cabecera acepta de 1 a 128 caracteres con el patrón [A-Za-z0-9._:-]. Genera una clave estable por intención de negocio, por ejemplo crm-pedido-0001-creacion. Si el request se corta después de enviarse, repite la misma clave, el mismo cuerpo y el mismo tenant para recuperar los mismos instance_id, operation_id y job_id. Generar una clave nueva tras un timeout puede crear una segunda intención.

Un cuerpo distinto con la misma clave devuelve 409. Usa una clave nueva solamente para una intención nueva, nunca para sustituir una operación uncertain. En ese caso conserva el UUID y consulta/reconcilia la misma instancia.

Seguir el aprovisionamiento

Una respuesta 202 devuelve instance_id (UUID estable de IACP), operation_id (intención), job_id (trabajo de cola) y normalmente status=queued. Conserva también X-Request-ID. Consulta GET /v1/operations/{operation_id} y GET /v1/instances/{instance_id}.

failedResultado terminal con errorConservar error_code, eventos y clave

Red, DHCP y acceso inicial

En los perfiles actuales el clúster MNG entrega DHCP sobre vmbr0. Tras crear o arrancar una VM, solicita POST /v1/instances/{instance_id}/network/discover para observar la red, POST /v1/instances/{instance_id}/network/initialize cuando el flujo autorizado lo requiera y POST /v1/instances/{instance_id}/access/verify para comprobar el acceso inicial. Guest Agent, Cloud-Init, SSH y DHCP pueden tardar o fallar de forma independiente; running no significa «listo para el usuario».

Lifecycle: consultar, encender, apagar y reiniciar

Consulta primero GET /v1/instances/{instance_id}/power. Para cambios usa POST .../power/start, POST .../power/shutdown o POST .../power/reboot, siempre con una Idempotency-Key nueva para esa intención. Los endpoints devuelven 202 y un operation_id; sigue el resultado y, ante uncertain, no repitas la mutación.

curl -sS -X POST 'https://iac.cyberfuel.com/v1/instances/<INSTANCE_ID>/power/start' \
  -H 'Authorization: Bearer TOKEN_DEL_TENANT' \
  -H 'Idempotency-Key: mvp-ubuntu-0001-start'

Eliminación autorizada

DELETE solo aplica a una KVM descartable propia, bajo una política vigente, apagada, sin locks y con autorización de eliminación. No aplica a VM 104, VM 106, Golden Image 29000 ni recursos fuera de la allowlist. El endpoint DELETE /v1/instances/{instance_id} requiere una clave nueva y un cuerpo con el operation_id de aprobación y el digest exacto plan_sha256; no acepta VMID, nodo ni force. La aceptación 202 no equivale a eliminación confirmada: sigue la operación hasta completed y verifica ausencia de la VM y consistencia de state.

{"operation_id":"<UUID_APROBACION>","plan_sha256":"<DIGEST_64_HEX_DEL_PLAN_REVISADO>"}

Errores y soluciones

400/422 Request incompatible o campo inválido; corrige el cuerpo sin reintentar una mutación ya admitida.401 Bearer ausente, inválido o expirado; vuelve a Authorize.403 Tenant, rol, propiedad o acción insuficiente; solicita la identidad adecuada.409 Conflicto de intención, nombre, estado, cuota o misma clave con otro cuerpo.429 Límite temporal; no generes otra intención, espera y conserva la clave si la solicitud pudo llegar.503 Admisión, persistencia o dependencia no disponible; repite la misma intención solo para recuperar una admisión no confirmada.

Ante timeout o uncertain, consulta primero la operación y la instancia, conserva instance_id, operation_id, job_id, Idempotency-Key y X-Request-ID, y escala a Infraestructura si hay lock persistente, divergencia con Proxmox, worker sin respuesta o estado no terminal. No borres state ni crees una VM sustituta.

Componentes y colas

FastAPI valida y registra la intención en PostgreSQL. Redis/Celery entrega trabajos; el IaC Worker ejecuta planes autorizados y el Lifecycle Worker procesa energía. Cada cola y worker tiene una responsabilidad separada; no se deben publicar tareas manuales desde Desarrollo.

Estados y reconciliación

EstadoInterpretación
pending/runningTrabajo admitido o en ejecución.
completedResultado terminal confirmado.
failedResultado terminal con error; conserva eventos.
uncertainNo repetir automáticamente; observar backend y reconciliar con autorización.

Usa operation_id, job_id, instance_id, X-Request-ID y timestamps para trazabilidad. Fallos recuperables se reintentan mediante la misma intención; locks anómalos, colas detenidas o discrepancias de state no se fuerzan.

Qué hacer y cuándo escalar

Ante una operación fallida, conserva la respuesta y evidencia, no crees un sustituto y no borres state. Escala a Infraestructura si existe uncertain, operación no terminal, lock persistente, error repetido de PostgreSQL/Redis, divergencia con Proxmox o worker sin respuesta.

Release y comprobaciones

Una release identifica commit, imágenes por digest, esquema, configuración y evidencias. El runtime actual usa 0011_crm_contract; las migraciones históricas no describen el estado vigente.

Promoción y verify

  1. Comprobar SHA ejecutado, salud, imágenes, colas, locks y operaciones no terminales.
  2. Usar iacpctl y go_live.py con manifiesto revisado, respaldo y evidencia privada nueva. El flujo incluye inventory, preflight, promote y verify.
  3. Después comprobar readiness, workers, PostgreSQL, Redis, Traefik, OpenAPI y autenticación.

Rollback seguro

El rollback cierra admisión y conserva PostgreSQL, Redis, state, historial y trabajos activos. No usa down -v, no borra estados ni fuerza desbloqueos. Una operación incierta sigue su procedimiento de recuperación y requiere Infraestructura.
