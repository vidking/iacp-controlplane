Una integración clara.

Crea y administra instancias mediante perfiles autorizados. Sigue cada solicitud hasta su resultado y conserva el control de su ciclo de vida.

Dos credenciales, dos alcances. HTTP Basic permite leer esta documentación. Para llamar a la API, pulsa Authorize e introduce solo el token Bearer del tenant, sin el prefijo. La clave de documentación no autoriza llamadas a /v1. La autorización no se conserva al recargar.
  1. Consulta perfiles. Selecciona un perfil disponible y una política vigente aprobada; no envíes IDs de infraestructura interna.
  2. Crea una intención. Envía POST /v1/instances con una Idempotency-Key nueva y conserva instance_id, operation_id y job_id.
  3. Sigue su estado. Un 202 confirma admisión. Consulta la misma operación hasta completed, failed o uncertain. Con start_on_create, comprueba también fulfillment y los datos de acceso.
  4. Administra Lifecycle. Utiliza start, reboot y shutdown sobre el UUID propio. Running no garantiza SSH, Cloud-Init ni disponibilidad de una aplicación.
  5. Elimina con autorización. Apaga ordenadamente y solicita DELETE bajo la política vigente. Espera el resultado terminal; no interpretes 202 como eliminación completada.

Reintentos: misma intención, misma clave y mismo cuerpo. Un cuerpo distinto con la misma clave devuelve 409. Ante uncertain, conserva el UUID y usa la reconciliación autorizada; no crees una instancia sustituta.

Los códigos aplicables se indican en cada operación. Conserva X-Request-ID para soporte; la lista de instancias devuelve X-Total-Count. Los ejemplos son sintéticos: sustituye las referencias por recursos autorizados.

◎Operaciones y diagnósticoEstados, trazabilidad y respuesta segura ante fallosAbrir guía

IACP separa la API, la cola Redis/Celery, el IaC Worker y el Lifecycle Worker. La API registra la intención en PostgreSQL y devuelve un operation_id; los workers ejecutan fuera de la petición HTTP.

Una operación puede estar pending, running, completed, failed o uncertain. uncertain no significa éxito: conserva el identificador y requiere reconciliación por observación autorizada antes de reintentar.

Los eventos y X-Request-ID permiten seguir la trazabilidad. Ante colas detenidas, errores repetidos, locks no terminales o dudas sobre el estado de Proxmox, detén nuevos reintentos y escala a Infraestructura con los IDs y timestamps; no intentes desbloquear ni mutar state.

La guía completa versionada está disponible como referencia secundaria en Forgejo.

⇄Despliegue y rollbackResumen operativo seguro del Control PlaneAbrir guía

Una release identifica el commit exacto del Control Plane, sus imágenes por digest, el esquema vigente y el manifiesto privado de despliegue. El runtime verificado usa 0011_crm_contract; las referencias históricas a 0004 no describen el estado actual.

  1. Comprobar versión desplegada, imágenes, salud, colas, locks y operaciones no terminales.
  2. Usar únicamente iacpctl y go_live.py con manifiesto revisado, respaldo y evidencia nueva.
  3. Después, verificar readiness, workers, PostgreSQL, Redis, contrato OpenAPI y autenticación.

Un rollback cierra admisión y conserva PostgreSQL, Redis, state e historial; no borra trabajos ni fuerza locks. La recuperación de una operación incierta sigue su procedimiento específico y requiere Infraestructura.

El runbook administrativo completo está restringido; la versión fuente se enlaza en Forgejo.
