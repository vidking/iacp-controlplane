1. Acceso autorizado

El backend consumidor configura IACP_API_TOKEN como secreto de entorno y envía Authorization: Bearer. IACP reutiliza el tenant persistente asociado; no crea un tenant por solicitud. HTTP Basic protege esta documentación. La API requiere el Bearer opaco del tenant; en Swagger pulsa Authorize e introduce solo ese token. Al finalizar usa Logout en Authorize. No es un JWT ni la contraseña de documentación.

El token debe pertenecer a un tenant activo con permiso de creación, KVM 1 autorizado y cuota libre. Comprueba planes, imágenes y perfiles: exige disponibilidad efectiva de kvm-1, ubuntu-2404 y lab-dhcp. Si falta un derecho, solicita a Infraestructura la identidad o habilitación LAB mediante el procedimiento existente; no se crea una política por VM ni se envía su UUID.

2. JSON mínimo

JSON mínimo del piloto LAB KVM 1/2 para POST /v1/instances. Cambia el nombre por el tuyo y la contraseña por una única de 16–128 caracteres ASCII imprimibles. Para entrar por SSH agrega tu llave pública a ssh_public_keys; es opcional para la API. Nunca envíes la llave privada. El cURL inferior solicita esos datos y sustituye el marcador de contraseña. IACP resuelve lab-dhcp solo si está autorizado; puedes omitir commercial_context en este piloto sin generar un pedido ficticio. Las solicitudes completas existentes siguen siendo válidas.

4. Respuesta real: HTTP 202

Para integrar basta conservar instance_id y status y consultar GET /v1/instances/{instance_id}. Los identificadores técnicos permanecen disponibles para compatibilidad y soporte. Respuesta completa de la prueba KVM 1 del 25/10/2026, Costa Rica. Esa VM ya fue eliminada: estos identificadores son evidencia, no los de tu solicitud. Un 202 confirma admisión, no SSH listo.

{{pilot_response}}

Extrae tus identificadores del archivo recibido y conserva X-Request-ID de respuesta.headers:

INSTANCE_ID="$(python3 -c 'import json; print(json.load(open("respuesta.json"))["instance_id"])')"
OPERATION_ID="$(python3 -c 'import json; print(json.load(open("respuesta.json"))["operation_id"])')"
export INSTANCE_ID OPERATION_ID

5. Consultar progreso, resultado e IP

Consulta tu instancia con el instance_id recibido. Repite GET mientras status sea pending/provisioning. Para acceso, comprueba además access.status=completed e ip_addresses: ready por sí solo no confirma SSH. Ante failed o acceso failed/uncertain, detente y conserva la intención; no crees otra VM.

curl --fail-with-body -sS "$IACP_BASE_URL/v1/instances/$INSTANCE_ID" -H "Authorization: Bearer $IACP_API_TOKEN" -o instancia.json
python3 -m json.tool instancia.json

Para diagnóstico puedes listar operaciones o consultar la operación original, su normalized_status, error_code y fulfillment. Los IDs técnicos siguen disponibles para soporte y conciliación.

La dirección observada está en ip_addresses. Si la lista está vacía, solicita descubrimiento de red y sigue su operation_id antes de consultar de nuevo:

curl --fail-with-body -sS -X POST "$IACP_BASE_URL/v1/instances/$INSTANCE_ID/network/discover" \
  -H "Authorization: Bearer $IACP_API_TOKEN" -H 'Content-Type: application/json' \
  -H "Idempotency-Key: $IACP_KEY-network" -d '{}'

6. Acceder por SSH

Espera DHCP, Guest Agent y Cloud-Init; una VM running aún puede no estar lista. La contraseña inicial root sirve para consola del guest; root SSH por contraseña no se habilita. Este recorrido pide tu llave pública para verificar SSH; selecciona su llave privada correspondiente al conectar. Verifica la huella del host mediante el canal autorizado, no desactives la comprobación.

IACP_IP="$(python3 -c 'import json; a=json.load(open("instancia.json"))["ip_addresses"]; assert a, "Sin IP observada"; print(a[0])')"
read -r -p 'Ruta de tu llave privada correspondiente: ' IACP_SSH_PRIVATE_KEY_FILE
ssh -i "$IACP_SSH_PRIVATE_KEY_FILE" "root@$IACP_IP"

7. Consultar energía y ejecutar Lifecycle

Consultar energía. Para shutdown, start o reboot, ejecuta una sola acción cada vez y sigue su operación hasta terminar. Antes de reboot confirma que el guest está listo.

curl --fail-with-body -sS "$IACP_BASE_URL/v1/instances/$INSTANCE_ID/power" -H "Authorization: Bearer $IACP_API_TOKEN"
read -r -p 'Acción (shutdown, start o reboot): ' IACP_ACTION
case "$IACP_ACTION" in shutdown|start|reboot) ;; *) echo 'Acción inválida'; exit 1 ;; esac
IACP_ACTION_KEY="$IACP_KEY-$IACP_ACTION-$(python3 -c 'import uuid; print(uuid.uuid4())')"
curl --fail-with-body -sS -X POST "$IACP_BASE_URL/v1/instances/$INSTANCE_ID/power/$IACP_ACTION" \
  -H "Authorization: Bearer $IACP_API_TOKEN" -H 'Content-Type: application/json' \
  -H "Idempotency-Key: $IACP_ACTION_KEY" -d '{}' -o accion.json
OPERATION_ID="$(python3 -c 'import json; print(json.load(open("accion.json"))["operation_id"])')"
curl --fail-with-body -sS "$IACP_BASE_URL/v1/operations/$OPERATION_ID" -H "Authorization: Bearer $IACP_API_TOKEN"

Una clave por intención. Ante timeout conserva la misma clave y cuerpo; no vuelvas a generar IACP_ACTION_KEY indiscriminadamente. No envíes la siguiente acción mientras exista una operación incierta o activa.

8. Eliminar correctamente

Solo una instancia propia autorizada, apagada y sin operaciones activas. Espera el shutdown terminal antes del DELETE comercial con cuerpo {}. Los recursos protegidos quedan excluidos. No necesitas un UUID de aprobación comercial.

curl --fail-with-body -sS -X DELETE "$IACP_BASE_URL/v1/instances/$INSTANCE_ID" \
  -H "Authorization: Bearer $IACP_API_TOKEN" -H 'Content-Type: application/json' \
  -H "Idempotency-Key: $IACP_KEY-delete" -d '{}' -o eliminacion.json
OPERATION_ID="$(python3 -c 'import json; print(json.load(open("eliminacion.json"))["operation_id"])')"
curl --fail-with-body -sS "$IACP_BASE_URL/v1/operations/$OPERATION_ID" -H "Authorization: Bearer $IACP_API_TOKEN"
curl --fail-with-body -sS "$IACP_BASE_URL/v1/instances/$INSTANCE_ID" -H "Authorization: Bearer $IACP_API_TOKEN"

Repite GET hasta confirmar resultado terminal y estado deleted; la liberación real y conciliación del state se verifican por el flujo de IACP. Un 202 no demuestra eliminación. Si falla o queda uncertain, escala con los IDs, sin borrar state ni forzar locks. Solo después de terminar, limpia el token de la sesión con unset IACP_API_TOKEN.

Errores: 401 identidad; 403 permisos; 409 conflicto, cuota o estado; 422 JSON inválido; 429 límite temporal del proxy; 503 admisión/dependencia. Conserva la intención en reintentos. Abrir referencia Swagger y Try it out.

Alcance certificado

El CRM solicita planes; IACP autentica, autoriza, comprueba cuota/capacidad y ejecuta asíncronamente. Ubuntu 24.04 con KVM 1/2 completó creación, G6, DHCP, acceso, Lifecycle y eliminación en Fase G. El piloto es supervisado; resiliencia integral y HA no están certificadas.

Identidad y aislamiento

HTTP Basic para documentación y Bearer opaco para API. El tenant proviene de la identidad; no puede asignarse en el JSON. Authorize no amplía derechos. No publiques tokens ni contraseñas en tickets. Solo la llave pública se incorpora a la solicitud.

Catálogos, planes y redes

Consulta planes, imágenes y perfiles antes de cada intención. KVM 1/2 están certificados con Ubuntu 24.04; KVM 3/4 permanecen definidos y dependen de autorización/certificación. Ubuntu 26.04 y AlmaLinux 9/10 siguen pendientes, no disponibles. WAN estática permanece bloqueada. No envíes CPU/RAM/disco libres, política UUID, VMID, VLAN o datastore.

Intenciones y recuperación

Una Idempotency-Key por intención, misma clave y cuerpo ante timeout. 202 devuelve IDs de seguimiento. No sustituir una operación uncertain por una nueva VM. El bootstrap cifra temporalmente la contraseña y no la entrega al motor de aprovisionamiento. Si expira antes de la entrega, la recuperación autorizada conserva instancia e intención; una entrega incierta solo se observa/reconcilia.

Diagnóstico y recursos históricos

Conserva instance_id, operation_id, job_id, X-Request-ID, clave y error_code para escalar. Las instancias históricas mantienen trazabilidad; sus antiguos cuerpos de creación y UUID de política no se envían al contrato comercial actual. La administración de laboratorio es una herramienta técnica, no un requisito por cada VM. Operaciones y diagnóstico.

Componentes y colas

FastAPI valida y registra la intención en PostgreSQL. Redis/Celery entrega trabajos; el IaC Worker ejecuta planes autorizados y el Lifecycle Worker procesa energía. Cada cola y worker tiene una responsabilidad separada; no se deben publicar tareas manuales desde Desarrollo.

Estados y reconciliación

EstadoInterpretación
pending/runningTrabajo admitido o en ejecución.
completedResultado terminal confirmado.
failedResultado terminal con error; conserva eventos.
uncertainNo repetir automáticamente; observar backend y reconciliar con autorización.

Usa operation_id, job_id, instance_id, X-Request-ID y timestamps para trazabilidad. Fallos recuperables se reintentan mediante la misma intención; locks anómalos, colas detenidas o discrepancias de state no se fuerzan.

Qué hacer y cuándo escalar

Ante una operación fallida, conserva la respuesta y evidencia, no crees un sustituto y no borres state. Escala a Infraestructura si existe uncertain, operación no terminal, lock persistente, error repetido de PostgreSQL/Redis, divergencia con Proxmox o worker sin respuesta.

Release y comprobaciones

Una release identifica commit, imágenes por digest, esquema, configuración y evidencias. Esta revisión de código requiere el esquema {{schema_head}}. El cierre de Fase G verificó el esquema 0012_commercial_intents; comprobar siempre la versión realmente ejecutada. Aprovisionar una KVM es distinto de actualizar el propio IACP Control Plane (VM 104).

Promoción y verify

  1. Comprobar SHA ejecutado, salud, imágenes, colas, locks y operaciones no terminales.
  2. Usar iacpctl y go_live.py con manifiesto revisado, respaldo y evidencia privada nueva. El flujo incluye inventory, preflight, promote y verify.
  3. Después comprobar readiness, workers, PostgreSQL, Redis, Traefik, OpenAPI y autenticación.

Rollback seguro

El rollback cierra admisión y conserva PostgreSQL, Redis, state, historial y trabajos activos. No usa down -v, no borra estados ni fuerza desbloqueos. Una operación incierta sigue su procedimiento de recuperación y requiere Infraestructura. Volver al contrato histórico requiere un binario compatible con el esquema vigente; no implica deshacer VMs ni revertir el state remoto.
